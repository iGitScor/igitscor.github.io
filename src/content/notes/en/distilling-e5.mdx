I built Bucket List partly to improve my skills in machine learning, on a small scope. The app sorts a list into themed islands, in the browser, and the obvious model for that is multilingual-e5-small: it understands French and English and is good at comparing sentences. But it is about 140 MB to download, and it takes seconds to minutes to run on a phone. Nobody waits that long to see a list.

So the app works in three steps: keywords, a light model, and the full model. This note is about the light one, and how I made it.

<Callout title="What is an embedding?">

A way to turn a sentence into a list of numbers, so that sentences with close meanings get close numbers. “Climb Kilimanjaro” and “hike in the Alps” end up near each other; “learn to bake bread” lands far away. Sorting a list by theme then becomes a matter of comparing numbers.

</Callout>

## The recipe

I followed a method called Model2Vec. The idea is simple: instead of running the big model every time, you run it once, ahead of time, on every word piece, and keep the result in a table. After that, reading a sentence is just looking up its words in the table and averaging them.

My script, `distill-m2v.py`, does five things:

1. Streams about 6 million tokens per language from French and English Wikipedia.
2. Keeps the word pieces that cover 99.5% of that text, plus every piece of the texts the app itself classifies: 30,286 in all.
3. Embeds each piece with the teacher, multilingual-e5-small at a pinned revision.
4. Reduces the vectors to 256 dimensions with PCA, which keeps 91.0% of the variance, weights rare pieces higher, and stores them as int8.
5. Fits a linear map from those 256 dimensions back to the teacher's 384, on 150,000 snippets per language, so the light model's output lives in the same space as the full model's.

<Callout title="What are PCA and cosine?">

PCA squeezes many numbers into fewer while losing as little as possible: here, each word’s 384 numbers become 256, and 91% of the information survives. A cosine measures how closely two lists of numbers point the same way, from 0 for unrelated to 1 for identical. A fit of 0.903 means the small model’s numbers point almost where the teacher’s do.

</Callout>

The map fits with a cosine of 0.903. The file is 8.66 MB, small enough to ship with the site. The whole run takes about 15 minutes on a laptop CPU.

## What it costs

I wanted numbers, not impressions. So I tested it on 757 items the light model had never seen:

| Tier | Agrees with the full model | Matches the hand-sorted list |
|---|---|---|
| Keywords | 72.0% | 78.2% |
| Light model | 77.5% | 79.5% |
| Full model | — | 86.0% |

I read this table two ways. The light model beats keywords, but only by 1.3 points against the list sorted by hand. And it stays 6.5 points under the full model. For a first answer in milliseconds, it is a good deal. For the final answer, it is not, so the full model still downloads in the background when the device can afford it.

## What I would do the same way next time

- **Compare with people, not only with the big model.** Agreeing with the full model looks good; matching the list sorted by hand is what users feel.
- **Measure keywords first.** On short list items, a good list of keywords came within two points of a trained model. I should have measured that before building anything heavier.
- **Pin the big model's version.** Its version is in the name of the light model's file. If it changed quietly, the two models would disagree for no visible reason.
- **Try again, it's cheap.** Fifteen minutes on a laptop means testing another vocabulary size is an afternoon, not a project.
