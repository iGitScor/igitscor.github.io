## Why I built it

I wanted to improve my skills in AI, so I picked the Model Context Protocol. Most examples only use one of its building blocks, the tools. I wanted a project that needed every one of them, for a real reason.

For the subject, I chose KYB. It was one of my focus areas at Heropay, and it is a domain that many different businesses need. So the project is related to my work, but it was mostly built out of curiosity about AI.

<Callout title="What is KYB?">

Know Your Business: the checks a bank or a payment company must run before working with a company. Does it exist, who runs it, and what does it do?

</Callout>

A KYB check always starts with the same lookups: does the company exist, who runs it, what does it do, and what did we conclude last time? That is what the server does.

<Callout title="What is MCP?">

The Model Context Protocol is a common plug between AI assistants and other software. An assistant such as Claude connects to an MCP server, and the server offers it actions it can take and data it can read. Here, the server knows how to look up French companies and keep notes about them.

</Callout>

## What I built

An MCP server that searches the French company registry, through the public [recherche-entreprises](https://recherche-entreprises.api.gouv.fr/docs/) API, and keeps a review file for each company. Claude Code, claude.ai or any other MCP client can use it, on the same computer or over the internet.

| Building block | Names | What it is for |
|---|---|---|
| Tools | `search_companies`, `get_company`, `find_by_person` | Looking up the registry |
| Tools | `create_dossier`, `add_note`, `set_status`, `list_dossiers`, `get_dossier` | The review file and its notes |
| Tool | `archive_dossier` | Asks you to confirm first (elicitation) |
| Tool | `draft_risk_summary` | Asks your assistant’s model to write the summary (sampling) |
| Tool | `bulk_check` | Checks many companies, shows progress, and can be stopped |
| Resources | `company://{siren}`, `dossier://{id}`, `dossiers://{status}`, `naf://{code}` | Documents an assistant can read |
| Prompts | `kyb_review`, `compare_companies` | Ready-made reviews you pick from a menu |

## How it works

<Callout title="Tools, resources, prompts: what is the difference?">

Tools are actions the assistant can run, like searching for a company. Resources are documents it can read, like a dossier. Prompts are ready-made instructions a person picks from a menu, like “review this company”.

</Callout>

**Polite with the public registry.** Every call goes through one place, limited to 5 requests per second (the public limit is 7), with a one-minute cache. Directors’ birth dates are removed before anything leaves the server.

**Works with or without a database.** Review files are kept in memory, so the server runs with no setup at all, or in PostgreSQL to keep them.

**No model of its own.** When a summary is needed, the server asks the assistant’s own model to write it, and saves the result as a note.

**Nothing kept between requests.** Over the internet, the server remembers nothing between two calls, which is what lets it run on a serverless host.

<Callout title="What does stateless mean?">

The server remembers nothing between two requests: each one carries everything needed to answer it. That lets a hosting platform start and stop copies of the server freely, without losing anyone’s work.

</Callout>

It has 23 tests that run without the network, and each release publishes a Docker image.

## What was hard

- Understanding what each building block is for. Once it clicked, it was simple: tools act, resources are read, prompts package a workflow, and elicitation and sampling hand a decision back to you or to your assistant’s model.
- The protocol changed in July 2026, and most tutorials still show the old way. I had to rely on the official reference instead.
- Hosting reached into the design: running on a serverless host is only possible because the server keeps nothing between requests.

## What's still missing

Before opening the write tools to the public, the server needs proper sign-in (OAuth 2.1) and monitoring, and it should be published to the MCP Registry.
